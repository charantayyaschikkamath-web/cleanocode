# CampusTwin AI — Shared Contracts v1.0 (Proposed Freeze)

**Status:** architecture specification, awaiting team review and reconciliation with the actual repository. These contracts are not evidence that corresponding code exists yet. Any change after review must be raised as an explicit contract change with impacted consumers and tests.

## 1. Contract conventions

- API base path: `/api/v1`.
- JSON property names: `snake_case` for backend API and persisted JSON. Frontend TypeScript types should retain the exact JSON keys at the transport boundary, then may map them to idiomatic local names if justified.
- IDs: UUID strings unless a record is a stable configured key (for example `BLD-01`, `ROOM-101`). IDs are opaque to clients.
- Timestamps: RFC 3339 / ISO 8601 with explicit timezone; API and persistent timestamps are UTC, rendered in the browser's local timezone.
- Numeric values: finite decimal numbers only; reject NaN/Infinity. Use `Decimal` or integer base units for money/ledger calculations where practical. No implicit unit conversion.
- Nullable facts: `null` means unavailable/not configured/not computable; it must not be silently converted to zero.
- Collection endpoints: `limit` default 50, maximum 100; stable opaque `next_cursor` for pagination. Filters are explicit query parameters. New records return their persisted server representation.
- Provenance and health are separate: a `SIMULATED` value can be healthy simulated evidence; `REAL` can be stale or unavailable.
- Side-effecting operations must be idempotent where stated and use a request/idempotency key.
- REST persisted records are the source of truth. WebSocket messages are notifications, not a replacement for fetching authoritative records.

## 2. Shared enumerations

### 2.1 Provenance

- `REAL`: produced by an identifiable real source such as an actual meter or locally used camera inference result. Record the source identifier.
- `SIMULATED`: generated by a deliberate scenario/demo input. Label it visibly in every relevant UI and export.
- `DERIVED`: computed from other recorded facts by deterministic application logic. Include input/source IDs and formula/version.

Provenance describes origin, not correctness or verification status.

### 2.2 Source health

`HEALTHY | STALE | UNAVAILABLE | ERROR | UNKNOWN`

- `HEALTHY`: source is reachable and evidence passes the configured freshness/quality checks.
- `STALE`: a prior reading exists but is older than the configured source-specific limit.
- `UNAVAILABLE`: no usable evidence is currently supplied.
- `ERROR`: a known source/inference/parse failure occurred.
- `UNKNOWN`: quality could not be established.

Only `HEALTHY` readings can be used for action verification. `UNKNOWN`, `UNAVAILABLE`, `ERROR`, and `STALE` must not satisfy a normal/empty condition.

### 2.3 Core resource types

`ENERGY | WATER | WASTE | OCCUPANCY | ROOM_USE`

This is a resource/signal taxonomy. Room use and occupancy are supporting signals rather than utility-consumption units.

### 2.4 Reading source types

`ELECTRIC_METER | POWER_METER | WATER_METER | FLOW_METER | BIN_SENSOR | CAMERA_INFERENCE | MANUAL | SIMULATOR | DERIVED_RULE`

### 2.5 Event types

`likely_energy_waste | likely_water_anomaly | likely_bin_overflow | likely_inefficient_room_use | sensor_unavailable | evidence_insufficient`

### 2.6 Event severity/status

Severity: `LOW | MEDIUM | HIGH | CRITICAL`.

Event status: `OPEN | ACKNOWLEDGED | RESOLVED | FALSE_POSITIVE`.

Do not mark an event `RESOLVED` merely because an action command was acknowledged. Resolution policy must require the configured rule to no longer hold or an authorized operator resolution with a documented reason. Event status is distinct from action status.

### 2.7 Action status

`PENDING_APPROVAL | COMMAND_SENT | ACKED | VERIFYING | VERIFIED_SUCCESS | REJECTED | COMMAND_FAILED | ACK_TIMEOUT | VERIFICATION_FAILED | VERIFICATION_TIMEOUT`

The finite-state contract is in Section 8.

### 2.8 Copilot response mode

`LLM | CACHED | TEMPLATE`.

- `LLM`: output validated from a configured provider and grounded in the supplied facts.
- `CACHED`: a stored last-good response for the same request/facts version is returned and marked with its original timestamp.
- `TEMPLATE`: deterministic no-key/offline fallback built from validated facts.

Never label template output as LLM output.

### 2.9 Impact values

- `PROJECTED`: deterministic forecast based on explicit assumptions; not a verified outcome.
- `VERIFIED_SIMULATED`: scenario action met the configured verification condition using simulated readings; not measured campus savings.
- `MEASURED`: actual instrumented observations and a documented measurement method support the result. This status is out of scope unless a real integration and measurement plan are implemented and evidenced.

Projection records do not qualify as verified-savings ledger entries.

## 3. Common envelope and error response

### 3.1 Standard API error

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "The request does not satisfy the API contract.",
    "request_id": "0192d8d0-4a42-7c41-b6e5-9f0df1e21a01",
    "details": {"field": "min_power_w", "reason": "must_be_positive"}
  }
}
```

Recommended HTTP status mapping:

- `400`: invalid transition/request semantics.
- `404`: record does not exist.
- `409`: idempotency conflict, duplicate incompatible request, or conflicting state.
- `422`: schema/input validation failure.
- `429`: rate limit where implemented.
- `500`: unexpected server failure (redacted detail only).
- `503`: optional/system dependency currently unavailable.

Errors must never expose API keys, credentials, raw frames, internal file paths, or stack traces to clients. Log `request_id` and a redacted diagnostic server-side.

### 3.2 Common timestamps

Relevant records should distinguish:

- `observed_at`: timestamp associated with the evidence/reading, UTC RFC 3339.
- `recorded_at`: actual wall-clock time the application persisted the record, UTC RFC 3339.
- `time_domain`: `WALL_CLOCK | VIRTUAL` where comparing age or duration depends on the clock.
- `virtual_elapsed_seconds`: elapsed scenario time when `time_domain=VIRTUAL`, nullable for real-only sources.

For camera frames and physical-device availability, freshness is based on wall-clock age. For simulation persistence and action verification, virtual elapsed time can govern the scenario. Never calculate camera freshness from accelerated virtual time.

## 4. Core data schemas

The schemas below are JSON-level contracts. Backend Pydantic models and TypeScript transport types must agree field-for-field. UUID format validation may be implemented by the backend model; stable configured IDs are also permitted for buildings and rooms.

### 4.1 Building

```json
{
  "id": "BLD-01",
  "name": "Engineering Block",
  "campus_id": "CAMPUS-01",
  "status": "HEALTHY",
  "timezone": "Asia/Kolkata",
  "metadata": {"floor_count": 4},
  "created_at": "2026-10-15T12:00:00Z",
  "updated_at": "2026-10-15T12:00:00Z"
}
```

`status` is a derived display status using known health/event facts; document the formula in `ALGORITHMS.md`. Never use only color to communicate it. `metadata` is for non-secret optional attributes.

### 4.2 Room

```json
{
  "id": "ROOM-101",
  "building_id": "BLD-01",
  "name": "Embedded Systems Lab",
  "floor": 1,
  "capacity": 40,

  "created_at": "2026-10-15T12:00:00Z",
  "updated_at": "2026-10-15T12:00:00Z"
}
```

`capacity` and schedule are optional context, not proof of occupancy. `status` is `HEALTHY | WARNING | CRITICAL | UNKNOWN` and must be derivable from documented inputs.

### 4.3 Resource/sensor configuration

```json
{
  "id": "SENSOR-POWER-ROOM-101",
  "source_type": "POWER_METER",
  "resource_type": "ENERGY",
  "building_id": "BLD-01",

  "configuration": {"simulation_only": true},
  "updated_at": "2026-10-15T12:00:00Z"
}
```

Configuration values must be validated and versioned when they affect calculations/verification. Sensor identifiers are unique. Never log connection secrets embedded by future real adapters.

### 4.4 Sensor reading

```json
{
  "id": "READING-000001",
  "source_id": "SENSOR-POWER-ROOM-101",
  "source_type": "POWER_METER",
  "resource_type": "ENERGY",
  "building_id": "BLD-01",
  "room_id": "ROOM-101",
  "value": 820.0,
  "unit": "W",
  "observed_at": "2026-10-15T12:00:00Z",
  "recorded_at": "2026-10-15T12:00:01Z",
  "time_domain": "VIRTUAL",
  "virtual_elapsed_seconds": 600.0,
  "source_status": "HEALTHY",
  "freshness_seconds": 0.0,
  "provenance": "SIMULATED",
  "quality_flags": [],
  "metadata": {"scenario_run_id": "SCENARIO-0001"}
}
```

Rules:

- `value` must be finite; values below/above plausible bounds are accepted only if the resource config allows them and quality flags explain them.
- `unit` is required, explicit, and consistent with the resource type. No implicit unit assumptions.
- `observed_at` and `recorded_at` are always explicit timestamps. `time_domain` controls duration/freshness semantics; virtual elapsed time is nullable for wall-clock readings.
- `source_status` is from Section 2.2; `freshness_seconds` is computed, not supplied as a user assertion.
- `quality_flags` contains stable machine identifiers (for example `OUT_OF_RANGE`, `CLOCK_SKEW`, `DARK_FRAME`, `OBSTRUCTED`, `STALE_READING`).
- No images or raw frames are included in this schema.

Request:

```json
{
  "question": "Why did this alert happen, and what evidence is missing?",
  "event_ids": ["EVENT-000001"],
  "facts_version": "facts-v1",
  "request_mode": "AUTO"
}
```

Response:

```json
{
  "answer": "The event was triggered because the configured rule saw sustained power above its threshold while occupancy was marked likely empty. The inputs are simulated. Confirm occupancy evidence before acting.",
  "mode": "TEMPLATE",
  "facts_version": "facts-v1",
```

### 4.15 Report/export

Report metadata must include `id`, `format` (`HTML | CSV | JSON`), `created_at`, `period_start`, `period_end`, `source_event_ids`, `source_action_ids`, `source_ledger_ids`, `provenance_summary`, `assumptions`, `limitations`, and `file_reference` or generated payload. For CSV export, provide a companion metadata section/file documenting units and assumptions where the CSV cannot express them adequately. Do not claim PDF support until implemented and tested.

### 4.16 Health/preflight

Use explicit dependency states: `PASS | WARN | FAIL | NOT_CONFIGURED`. Response includes `checked_at`, `overall_status`, a list of `{name,status,message,repair_action,required_for_core_demo}`, and `optional_capabilities`. Missing optional LLM key or model weights should be a warning, not a fatal error for the simulated demo.

## 5. Unit and arithmetic rules

Supported initial units (expand via contract change):

- Power: `W`, `kW`.
- Energy: `Wh`, `kWh`.
- Flow: `L/min`, `L/s`, `m3/h` only when explicit conversion is implemented.
- Volume: `L`, `m3`.
- Count: `count`, `persons`.
- Time: `s`, `min`, `h`.
- Cost: configured currency such as `INR`, with `currency` always explicit.
- Emissions: `kgCO2e`.

Energy formula:

`kWh = (power_watts / 1000) × duration_hours`

For a constant 1000 W load over 600 seconds: duration = 600/3600 = 1/6 hour; kWh = 1000/1000 × 1/6 = 0.1666667 kWh (rounded for display only). This result is independent of the acceleration multiplier if the virtual duration is unchanged.

`estimated_cost = kWh × configured_tariff_per_kWh`

`estimated_CO2_kg = kWh × configured_CO2_factor_kg_per_kWh`

Tariff and factor may be null. In that case the corresponding result is unavailable, not zero. Store formula version, exact input values, units, interval, configuration/factor version and source IDs.

Water consumption/anomaly calculations require a validated flow unit and interval. A flow alert does not automatically imply saved water volume. For waste/bin events, do not invent mass, diversion, cost, or emissions without configured and supported factors.

### 6.1 Response rules by endpoint family

- List responses: `{ "items": [...], "next_cursor": null }` plus any documented filter summary.
- Detail GETs return the persisted record (plus explicitly documented relationships), or standard `404`.
- Create/transition POSTs return the resulting persisted state, not an optimistic success stub.
- `/actions/{id}/approve` repeats with the same idempotency key return the original action/result. A conflicting retry is `409`.
- `/scenarios/run` returns only IDs/outcomes actually persisted by the scenario runner.
- No route returns raw camera frames. Camera image bytes are never accepted by report/copilot routes.
- Time/range filters are inclusive-start/exclusive-end UTC intervals and require `start < end`.

## 7. WebSocket and polling behavior

Envelope:

```json
{
  "schema_version": "1.0",
  "message_id": "WS-MSG-000001",
  "type": "event.created",
  "emitted_at": "2026-10-15T12:05:00Z",
  "entity_type": "event",
  "entity_id": "EVENT-000001",
  "version": 1,
  "payload": {"event_id": "EVENT-000001", "status": "OPEN"}
}
```

Initial message types: `reading.created`, `event.created`, `event.updated`, `action.updated`, `verification.updated`, `ledger.created`, `scenario.completed`, `system.health_changed`.

Clients must reconnect with backoff, ignore duplicate `message_id`s, and refetch the authoritative REST record after a relevant notification. If WebSocket is offline/unavailable, poll the active view on a configurable interval and show a visible stale/reconnecting indicator. The app must remain usable without WebSockets.

## 8. Action state machine and invariants

### 8.1 Allowed transitions

| From | To | Trigger |
|---|---|---|
| `PENDING_APPROVAL` | `COMMAND_SENT` | A valid human approval is persisted and the simulator/hardware adapter dispatches a command |
| `PENDING_APPROVAL` | `REJECTED` | Human rejection with reason |
| `COMMAND_SENT` | `ACKED` | The receiver/simulator explicitly acknowledges the command |
| `COMMAND_SENT` | `COMMAND_FAILED` | The dispatch operation definitively reports failure |
| `COMMAND_SENT` | `ACK_TIMEOUT` | No acknowledgement before configured acknowledgement timeout |
| `ACKED` | `VERIFYING` | Verification starts and immutable pre-action baseline is associated with the action |
| `VERIFYING` | `VERIFIED_SUCCESS` | Required healthy post-action evidence satisfies the configured comparison |
| `VERIFYING` | `VERIFICATION_FAILED` | Adequate healthy post-action evidence contradicts the success condition |
| `VERIFYING` | `VERIFICATION_TIMEOUT` | Verification window expires without sufficient outcome evidence |

No other state transitions are legal. Terminal states are `VERIFIED_SUCCESS`, `REJECTED`, `COMMAND_FAILED`, `ACK_TIMEOUT`, `VERIFICATION_FAILED`, and `VERIFICATION_TIMEOUT`. `VERIFIED_SUCCESS` is not reversible; corrections require a new auditable compensating record, not mutation.

### 8.2 Transition invariants

1. Human approval is required before a command can be dispatched in demo mode.
2. Persist transition and state change atomically in one DB transaction.
3. Every transition has a matching append-only audit row.
4. A duplicate approval with the same idempotency key does not dispatch a second command.
5. `ACKED` is never treated as successful outcome.
6. A baseline is stored before dispatch or before the state moves into verification; exact ordering must ensure it reflects pre-action conditions and cannot be overwritten by post-action data.
7. Only `VERIFIED_SUCCESS` qualifies for a verified savings ledger entry.
8. At most one ledger entry may be created for an action/verification pair; enforce with a database uniqueness constraint and transaction.
9. If any part of verification/ledger write fails, do not leave a success UI with a missing or duplicated ledger. Reconcile atomically or use an idempotent transactional service.
10. Failure, rejection, timeout, stale evidence, or missing evidence creates no savings entry.
11. A retry after a terminal action creates a new action linked to the prior action; it does not reopen the old one.
12. No real actuator can be invoked unless a real, explicitly configured adapter is implemented and authorized. The default demo path must use a simulator.

## 9. Independent verification contract

The verifier must:

1. Capture immutable pre-action baseline samples from the configured metric/source. Default simulated demo policy: take at least three healthy compatible samples over the baseline window and use the median. This is a tunable demo default, not a universal physical measurement standard.
2. Record reading IDs, units, source status, provenance, and the algorithm/version used.
3. Dispatch the command only after human approval.
4. Wait through the configured virtual observation window (simulation) or wall-clock window (real adapter), using the correct clock domain.
5. Require at least three healthy post-action samples compatible with the same metric/source and interval. If not available before timeout, return `VERIFICATION_TIMEOUT` or `INSUFFICIENT_EVIDENCE`; do not guess.
6. Calculate `observed_drop_percent = ((baseline - post) / baseline) * 100` for a lower-is-better metric where baseline is greater than zero. If baseline is zero or missing, the condition is not computable and cannot succeed.
7. Compare the result to the configured `required_drop_percent` and any safety/business predicates. A successful command or ACK is not part of this numeric comparison.
8. Record all post reading IDs, summaries, required/observed drop, interval, and result.
9. Transition to `VERIFIED_SUCCESS` only if the comparator passes and all quality requirements pass.

For increasing-is-better metrics, water volume, bin overflow, or other intervention types, define a separate named comparator and unit-aware policy. Do not reuse the energy drop calculation blindly.

### Simulator outcome modes

- `SUCCESS`: ACK received and post readings satisfy the criterion.
- `DROP_COMMAND`: no ACK; action ends `ACK_TIMEOUT` unless dispatch itself definitively errors (`COMMAND_FAILED`).
- `ACK_IGNORE`: ACK is received but post readings remain above required threshold; action enters `VERIFYING` then `VERIFICATION_FAILED`.

The demo must visibly show the baseline, required change, observed change, observation window, evidence freshness, and final status.

## 10. Impact ledger and calculation policy

### 10.1 Ledger eligibility

Projections belong in facts/reports/what-if responses and do not count as savings ledger entries. An eligible `VERIFIED_SIMULATED` entry is created only after the matching action reaches `VERIFIED_SUCCESS` and the verification record is complete. For a real `MEASURED` entry, a separate future contract review must define the measurement method, real source provenance, calibration/measurement quality, and audit requirements; do not imply this mode is available by default.

### 10.2 Energy

For constant load power `P_w` over interval `t_h`:

`kWh = (P_w / 1000) × t_h`

For a savings delta based on a verified post/pre change over interval `t_h`, use the configured baseline minus post value and name the formula clearly:

`delta_kWh = max(0, (baseline_W - post_W) / 1000) × verified_duration_hours`

This is a scenario estimate under the assumption that the observed power delta persisted through the stated interval. If the rule requires both a threshold and persistence, only the verified interval is eligible. Do not multiply a momentary sample delta by an arbitrary day/week/month.

### 10.3 Cost and CO₂e

`estimated_cost = delta_kWh × tariff_per_kWh`

`estimated_CO2_kg = delta_kWh × co2_factor_kg_per_kWh`

Both results are unavailable if their factor is null, incompatible, or unversioned. Currency is explicit (`INR`, etc.); CO₂ unit is `kgCO2e`. Factors and calculation configuration are versioned.

### 10.4 Ledger immutable input snapshot

Each entry records: action/event/verification IDs, actual source reading IDs, exact numeric inputs, units, formulas/version, factor/configuration version, interval, provenance, assumptions, creation timestamp, and all outputs. Corrections must be appended as adjustment/reversal entries if later evidence warrants them; do not rewrite historical entries.

## 11. Detection rules and evidence requirements

- `likely_energy_waste`: requires a documented occupancy signal (may be `SIMULATED`) indicating `LIKELY_EMPTY`, compatible power reading above configured threshold, and persistence duration. If occupancy evidence is unknown/unhealthy, emit `sensor_unavailable` or `evidence_insufficient`, not an empty-room claim.
- `likely_water_anomaly`: requires a configured flow rule (threshold/persistence and/or a named scenario-defined pattern) with explicit flow units and wall/virtual time domain. The default production value must not invent a campus-specific safe threshold.
- `likely_bin_overflow`: real detection only if a licensed local detector/data path is available and tested; otherwise create a user-visible `SIMULATED` scenario/manual event.
- `likely_inefficient_room_use`: requires configured and documented occupancy/schedule/capacity/power signals; missing schedule or occupancy cannot be treated as evidence of inefficiency by itself.
- `sensor_unavailable`/`evidence_insufficient`: represent inability to infer reliably; do not classify unavailable as normal or anomaly.

Use deterministic threshold + persistence for hackathon scenarios unless a real evaluated model is ready. Do not label thresholds as trained ML. Never invent a confidence score for a deterministic rule.

## 13. Security, privacy, and resilience

- Validate route payloads and query bounds; limit list sizes and scenario durations.
- Restrict CORS to configured origins.
- Keep provider/API credentials in environment configuration; redact values from logs.
- Camera frames remain in memory; never persist, log, attach to reports, send to LLM, or place in error messages.
- Persist only necessary derived occupancy counts/status and event evidence.
- If camera permission, frame freshness, lighting/coverage, model weights, or inference fails, report `UNKNOWN`/`UNAVAILABLE`.
- No dependency or model-weight download at application startup.
- If WebSocket fails, continue over REST/polling.
- If provider fails, timeout/retry at most once and use useful template fallback.
- Reset operates only on isolated demo data and requires explicit confirmation.
